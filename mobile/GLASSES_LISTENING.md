# Glasses wake capture

Settings → Glasses → Listening is an independent account-scoped opt-in. It replaces continuous speech transcription. On upgrade, private `glasses-transcripts` logs are deleted and their old counters removed; listening is disabled until the user chooses the Digital Brain storage folder and explicitly enables the new capture behavior. Previously exported user files are not searched or deleted. Manual recordings keep their existing behavior.

## Detection

Android native ownership and firmware VAD remain unchanged. Valid 16 kHz mono signed little-endian PCM passes the firmware speaking gate and the persisted minimum-volume gate before reaching Sherpa. The relative volume scale remains 0–100 (-60 to -20 dBFS), with 0 disabling the volume filter. The gate requires five consecutive 20ms loud-enough windows; once opened, it stays open for the utterance to retain quiet phonemes. A bounded four-second PCM onset ring is replayed at gate opening. Quiet utterances never request transcription. The foreground screen retains the received-audio meter; it cannot show firmware-suppressed sound.

The active Sherpa model is the personal acoustic fine-tune `wake-word-personal-2026-10-15`, selected as epoch 3 on October 15, 2026. It updates the encoder front end, Zipformer encoder, predictor and joiner of the matching 2025 zh-en 3M KWS model. Assets live in `android/src/main/assets/wake-word-personal-2026-10-15/`, with model provenance, SHA-256 hashes and runtime settings in `model-manifest.json`. Use keyword score **0.000001** and threshold **0.35** with these weights; the previous model's score 1 is unsuitable. Keep 16 kHz/80 feature dimensions, dither 0, one CPU thread, 16 search paths and one trailing blank. The original phrase aliases remain `hey_brain` and `okay_brain`; rejection keywords never activate capture. This is acoustic wake detection, without an embedding verifier or wearer authentication. See [WAKE_WORD_MODEL.md](WAKE_WORD_MODEL.md) for evidence and rollback. Upstream model source: <https://www.modelscope.cn/models/pkufool/icefall-kws-zipformer-zh-en-3M-2025-12-20>.

One native serial executor owns all Sherpa contexts/streams and a bounded 64-event PCM/VAD queue per session. Overload or more than one second of queued input invalidates the session and asks the user to toggle listening again; stale audio never activates later. Generations reject callbacks after pause, calls, disconnect, recording, OTA, disable and account changes. Unknown PCM loss for three seconds discards any partial capture only when no VAD silence is known; expected suppressed silence uses the active endpoint deadline without microphone recovery or a tight polling loop. VAD silence does not restart the microphone. When quiet PCM is suppressed, a short synthetic zero tail allows the decoder to emit its trailing blanks; those samples never enter the saved WAV. Silent utterance resets release/recreate the decoder stream once, without continuous inference or a permanent wake lock.

Upstream model-weight redistribution terms remain unverified, as recorded in the original V8 documentation; the fine-tuned assets remain in the existing personal device test workflow.

## Command capture

An accepted wake calls the public `MentraBluetoothSdk.rgbLedControl` API from a coroutine using green, 250ms on, zero off, one blink and null package name; an accepted execution result asynchronously requests the same short blink in orange, while rejected/unknown/failed/not-configured commands never trigger it; green replaces blue while the reported blue failure is investigated. No LED-specific SDK patches, custom dispatcher, raw UART commands or framing override remain. The coroutine bounds the optional response wait at five seconds without blocking capture. Native diagnostics count requests and dispatch errors; response timeout is not proof that a command was not sent. The LED command builder in installed SDK 3.2.1 was compared against downloaded 0.1.21-beta.5 and is identical ignoring whitespace. The six-second cooldown uses monotonic time from the accepted wake. Detection is bypassed during capture, so additional wake phrases do not split a command. It resumes after completion, subject to the remaining cooldown.

Capture includes up to four seconds of received pre-roll, preserving the wake phrase and an immediately spoken command; it may include preceding speech. The maximum saved PCM is thirty seconds. A capture initially allows four seconds of firmware-reported silence after the wake. After at least 300ms of sustained post-wake firmware-reported speech PCM, subsequent silence ends capture after 1.5 seconds. The onset counter resets on VAD silence, so brief wake tails, the 120ms wake cue and isolated blips do not consume the longer allowance. This acoustic phase transition is not semantic word recognition; exceptionally short command speech may retain the longer cutoff, without losing its audio. The user minimum-volume gate applies only before wake acceptance; it never classifies quiet command PCM as silence. Both same-breath commands and commands after a pause keep all received PCM. The thirty-second time/byte limit is unchanged. Native timers are deadline-based and best-effort under Android sleep. Calls, disconnect, OTA, manual recording and disable discard unfinished capture without saving a partial file. Audio never received from the glasses cannot be reconstructed. Timestamped JSON distinguishes received audio duration from wall-clock start/end; suppressed silence is not filled into the WAV.

## Transcription and storage

Only completed wake captures enter the bounded four-job transcription queue. One native worker stages the WAV privately and sends it through the authenticated frontend `/mobile/glasses/transcribe` proxy to the GPU `whisper-large-v3-turbo` provider. Provider URL/key default to the main LLM settings, with optional `SPEECH_BASE_URL` / `SPEECH_API_KEY` overrides. There is no phone or CPU-server transcription fallback. Native HTTP has five-second connect/twenty-five-second read timeouts, cancellation on generation/account/eligibility changes and a thirty-second watchdog under the existing ninety-second wake limit. Results are matched locally; stale/interrupted/offline requests never execute or enter an upload/action retry queue. Failed captures retain safe failure metadata and can be saved, never retranscribed/executed by recovery. Chat dictation uses the same GPU adapter through its separate foreground dictation route. No background path uses JS or Headless JS.

On upgrade, Listening is disabled once because its previous opt-in described local-only recognition. The screen now states that command audio is sent to the user's server. Re-enable from the foreground after installing the new native build. No Whisper model is downloaded or required for glasses setup. Wake detection and its personal Sherpa assets remain entirely native/local; idle PCM is never uploaded.

A completed capture is first staged atomically with fsync in private account-scoped recovery storage, then transcribed and copied to `<Digital Brain>/Wake captures` as matching timestamp/UUID `.wav` and `.json` files. JSON contains capture/wake/end timestamps, capture timezone, English language, transcript, received audio duration, completion reason and transcription outcome/duration. Raw PCM stays bounded in memory until completion; persisting completed wake audio is explicitly user-authorized. Failed transcription retains the WAV and an explicit outcome for analysis. SAF copy lengths and streaming SHA-256 checksums are checked before private cleanup. Target URIs are journaled for retry without creating a second filename pair. Only JSON metadata marks the final transcription outcome; consumers should wait for both matching files.

Failed copies retain private originals and expose Retry saving; process-recovered pending transcription is marked interrupted when exported by retry. Active inference files are excluded from concurrent retries. At four pending recovery captures, listening pauses until saves are retried. The directory is account-scoped; retry accesses only the signed-in account. Completion receipts keep the last 32 identifiers to avoid duplicate counter increments after interrupted cleanup. Sign-out cancels queued inference and suppresses stale callbacks. Existing completed captures remain user files.

No audio, transcript text, storage/network identifiers, raw exceptions or account identifiers enter general diagnostics, system logs, analytics, Mirador or backend requests. Safe diagnostics retain VAD/wake/quiet/drop/error/LED counts, capture state and inference/audio durations. There is no automatic command execution or upload.

## Validation

JVM tests cover VAD/volume ordering and onset replay, wake plus immediate/delayed command, four-second initial and 1.5-second command silence, brief-cue rejection, expected VAD silence beyond the transport-loss threshold, six-second cooldown, repeated wakes during capture, interruption discard, thirty-second byte limit, unknown transport loss, synthetic decoder-tail exclusion, ring wrapping and WAV headers. Run native Java/Kotlin compilation/tests, release manifest processing and mobile TypeScript/lint/format checks.

Device validation remains required: Sherpa JNI inference on delivered glasses audio, onset clipping, alias recall, quiet speech and noisy environments, exact command endpointing, locked-phone capture/transcription, SAF writes/retries/process recovery, sign-out and call/recording/OTA/disconnect races. Compare quiet and conversational phone/glasses battery against connection-only and prior listening sessions. Host compilation and replay are not evidence of hardware accuracy or power consumption.

## LED validation and diagnostics

Device testing reported that red, green, orange and white work but blue fails even with a three-second hold. The manual light-test panel is removed at user request. Automatic wake feedback uses the public SDK RGB API with green quick-blink arguments; blue behavior remains unresolved. Historical manual-test presets and observations remain available in native diagnostics.

A persistent bounded 150-event `ledFeedback` trail retains safe request/outcome diagnostics: attempt sequence, timestamps, source/result enums, color, pattern, exact on/off milliseconds, count and response time. Historical manual-test observations remain readable. No request UUID, package, raw response/error, audio or transcript is exported. No LED-specific SDK patch, framing override or raw UART command remains.

A successful SDK reply or timeout alone does not prove physical visibility. Device confirmation establishes the observed light behavior; host compilation and tests do not establish hardware performance or battery consumption.

## Audible feedback

Listening adds two finite app-owned PCM cues alongside the existing LEDs: a 120ms single tone on Sherpa wake detection, and a 280ms rising double tone only after accepted execution. Wake cues accompany the green blink even if later transcription validation rejects the capture. Execution cues accompany the orange blink, never a mere phrase match or failed/unknown/not-configured result.

Both reuse `GlassesAlertPlayback` and its verified glasses-only Bluetooth media output. Calls have priority; notifications cannot interrupt the short cues. Use the existing chime volume, transient ducking focus, route verification and completion/disconnect/sign-out/disable cleanup. Android media mute/DND remain effective, with no phone-speaker fallback or system-volume changes. Explicit listening feedback does not require notification alerts, an allowed notification app, a locked screen or the notification cooldown. No idle audio session/polling is added and microphone capture is not paused; on-device testing must check cue audibility, route startup latency and acoustic interference with immediate commands.

These generic app cues are separate from the photo shutter, which remains firmware-owned through the SDK camera path below. Bluetooth media pairing/output must be available for app cues even when the BLE control connection works. During initial route selection, old/empty/multiple outputs remain muted until the existing 1.5-second verification deadline; they must not abort the asynchronous preferred-device switch prematurely. After verification, route loss or additional outputs stop playback immediately. Use the existing Alerts Test chime and last playback error to distinguish missing media pairing, mute/DND, focus failure and route verification failure. Diagnostics retain the bounded playback state/error, never audio or transcript content.

## Known commands

Completed English transcripts are validated and matched locally before action dispatch. The transcript must start with Hey/Okay/OK followed by Brain or a narrow phonetic alias (Brane, bring, Brian). Wake matching is exact or fuzzy after case/punctuation normalization, stays anchored at the start, and is not speaker authentication. Unrelated near words such as rain/train are rejected; a wake with no command never executes. Unknown commands and rejected wakes retain the same WAV/JSON capture but execute nothing. No LLM is called.

| Command | Aliases | Execution |
| --- | --- | --- |
| Open front gate | Open front door, open the door, front gate, front door; from dore as a bounded whole-phrase transcription alias | Fixed backend action invokes the configured Home Assistant script. |
| Toggle car gate | Toggle car door, open the car gate, car gate | Fixed backend action invokes the configured Home Assistant script. |
| Take a picture | Take a photo, take a pic, take a peek (transcription alias) | Native SDK save-only capture, followed by existing original-media sync. |

The pure `GlassesCommandMatcher` v3 matches an ordered full-utterance grammar. Case, punctuation, optional articles and leading/trailing please are canonicalized. Existing aliases use the same normalized form. Protected actions and targets are exact; known fused target/noun pairs can receive one boundary repair. Non-critical tokens may use the bounded spelling, adjacent-transposition and vowel-preserving phonetic budget. Negation, questions, deferred commands, repeated wakes, extra words and multiple commands are rejected. Only a sufficiently close, uniquely separated intent is accepted. Cost is not a probability; field rejection thresholds still require held-out recordings. Private capture JSON records matcher version, stage, cost, margin and rejection reason. See [GLASSES_SPEECH_EVALUATION.md](GLASSES_SPEECH_EVALUATION.md) for replay comparisons and limits.

`GlassesCommandExecutor` runs on the bounded native speech worker. It checks the original listening generation, active/armed enablement and account before dispatch; call/OTA/recording/disconnect/disable/sign-out invalidate pending action eligibility. Commands older than ninety seconds expire rather than executing later. Private capture JSON schema v2 stores `wakeVerified`, `wakeMatch` (exact/fuzzy/missing), `commandMatch`, `command`, `commandRequestId` and `commandStatus` alongside the transcript. Command and match outcomes include rejected/unknown/cancelled/expired results. Retry saving and process recovery only save files; they never dispatch commands again. An interrupted dispatch can retain `dispatching` when its outcome is unknown.

Gate requests use the existing fresh native Google ID token and configured frontend proxy at `/mobile/glasses/commands`. Only a fixed intent, random request UUID and capture timestamp leave the phone. The backend owns script selection via `GLASSES_FRONT_GATE_SCRIPT` / `GLASSES_CAR_GATE_SCRIPT`; Home Assistant owns the two-second relay pulse. Backend configuration and durable at-most-once receipts are described in [GLASSES_COMMANDS.md](../backend/orchestrator/docs/architecture/GLASSES_COMMANDS.md). No offline queue, automatic network retry or LLM fallback is used. Accepted means Home Assistant accepted the script request, not that a gate sensor confirmed movement.

Photos use public native SDK camera APIs only, with no bundled PCM or phone media playback. After a verified photo command, request a short PHOTO/MAX camera warm-up lease with matched ZSL/MFNR settings, wait up to eight seconds for camera_status ready, recheck the original listening generation/account/connection, then request an original save-only gallery photo with sound=true. The firmware's warm-camera feedback path plays its own exposure-time snap without cold-start preparation clicks. Release the request-owned lease in finally; no idle camera warming or polling is added. A fifteen-second firmware lease bounds cleanup even if the phone disconnects.

If warm-up is unavailable or times out, preserve capture with sound=false rather than introducing preparation sounds; the content-free connection trail records photo_camera_warmup ready/unavailable. This behavior needs validation against the installed glasses firmware, including whether its warm capture path skips preparation sounds. Existing photo-status events and a scheduling fallback feed normal gallery/Immich sync. The optional photo response wait is bounded to ten seconds; absent replies never cause an automatic second photo. No scene analysis is enabled.

Configuration failures preserve a safe `commandConfigurationIssues` list in private capture JSON: phone_api_configuration_missing, ha_url_missing, ha_token_missing, script_entity_missing or script_entity_invalid. Dispatch events distinguish phone configuration from backend configuration. Backend script values must be callable script.* entities, not the fixed Digital Brain intent names; env-file updates require recreating the running backend container. Orange feedback means the command endpoint/photo API accepted execution, not proof of physical gate movement. LED requests remain nonblocking and content-free in the persistent trail under COMMAND.
